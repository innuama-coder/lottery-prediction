# 阶段 0 数据可行性计划修订 1.4

## 修订结论

阶段 0 的完成条件改为“当前证据能否支持数据可行性判断”，不再等待未来开奖周期。原 1.3 合同和证据保持原样，作为历史基线；本修订只改变从现有证据得出阶段结论的方法。

跨期开奖监测继续运行，但属于非阻塞的运行观察。它只能补充真实环境中的准时性和短期可用率，不能补足历史覆盖，也不能替代来源合规、解析重放和故障记录测试。

## 根本原因

1. 1.3 计划把验收对象定义为数据可行性，却在 P0-06 要求至少两个完整开奖周期。
2. P0-06 阻塞 P0-07，而 `G-RECOVERY` 又是 `PASS_FULL` 和 `PASS_LIMITED` 的共同前置门。
3. 因此，即使来源、解析、故障记录和覆盖量已经可以判断，最终结论仍会被未来截止时间强制改成 `HOLD`。
4. 这把“采集系统是否正确”和“未来运行是否持续稳定”误当成同一个问题。

## 修订后的工作边界

阶段 0 现在回答五个问题：

1. 当前有哪些官方发布端，普通 HTTPS 访问是否可用，访问限制是否被如实记录；
2. 已保存的历史页面能否完整、确定、重复地解析；
3. 超时、拒绝访问、畸形页面、哈希冲突和重复证据能否立即失败并留下真实状态；
4. 是否存在两个可访问且相互独立的来源，可以进行真正的冲突检测；
5. 当前历史覆盖是否足以把数据交给后续建模研究。

阶段 0 不回答未来数月的生产 SLO，也不训练、选择或评价预测模型。

## 即时验收项

| 验收项 | 方法 | 通过或完成标准 |
| --- | --- | --- |
| 来源可用性快照 | 读取来源目录中的最近一次合规访问观测及访问策略 | 每个来源均有时间、HTTP 状态或政策阻断原因；不把受阻来源写成可用 |
| 采集与解析可重复性 | 对保存的大乐透、双色球 fixture 重复解析，并离线重放真实保存样本 | 相同输入产生相同规范化结果；缺字段、越界、重复号、编码损坏均被拒绝 |
| 失败记录真实性 | 运行故障注入、哈希篡改、重复 evidence ID、写入冲突测试 | 失败不产生 verified 记录；旧原文和旧事件不被覆盖 |
| 来源拓扑与冲突能力 | 检查来源角色、可访问性和共享上游说明 | 只有在两个独立、可访问、实际含数据的来源存在时才声称可做独立冲突检测 |
| 建模数据充分性 | 机械计算目标区间和最低区间的预期、已观察、缺失数量 | 两种彩票至少达到冻结的最低覆盖区间，才能进入阶段 1；否则阶段 0 完成但项目 `HOLD` |
| HOLD/STOP 分类 | 审查每种彩票是否仍有具体合规修复动作，以及官方证据替代路径是否已经穷尽 | 有动作且未穷尽才是 `HOLD`；`STOP` 必须列全已审计替代项并提供非空穷尽证据；所有引用必须存在于仓库并进入报告哈希闭包；矛盾或缺失分类直接失败 |

## 非阻塞观察轨道

原 `P0-06` 的 24 次请求计划保留，状态改为 `supplementary_non_blocking`：

- 不再阻塞即时评估报告；
- 不参与当前 `GO/LIMITED_GO/HOLD/STOP` 的机械选择；
- 只追加记录按期开奖时刻的真实请求、延迟、HTTP 状态和恢复情况；
- 完成后作为附录更新，不追溯改写本次阶段结论；
- 若发现新事实，只能通过新的修订事件影响后续决策。

## 决策规则

- `GO`：两种彩票均有合规、可重复的权威数据路径，并达到目标历史覆盖。
- `LIMITED_GO`：至少一种彩票达到最低历史覆盖且其他即时硬门通过；只把通过的彩票交给阶段 1。
- `HOLD`：当前不能交给阶段 1，但存在明确、合规、可执行的补数或来源修复路径。
- `STOP`：合规替代方案已经审计完毕，仍不存在权威数据路径，除非绕过控制或以第三方数据替代官方事实。

`HOLD` 和 `STOP` 都是完整、可验收的阶段 0 结论，不表示阶段 0 尚未完成。

## 独立验收方法

1. 校验报告 JSON Schema；
2. 重新计算全部输入文件 SHA-256；
3. 重新运行报告中的两组离线测试命令；
4. 重新计算覆盖数量与来源可用性分类；
5. 确认 `prospective_observation.blocking=false`；
6. 确认项目结论只由即时验收项推导。
